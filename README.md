# Myraha Spend Server

Постійний сервер для Ubuntu/Debian: приймає дані розширення, збирає денний спенд Facebook через проксі та оновлює витрати Keitaro з комісією. Панель українською, вхід одним паролем.

## Що вже реалізовано

- `POST /fb_data/add` за [server-api.md](server-api.md): schema 2/3, `X-Client-Key`, заміна повного списку cookie, збереження попереднього token/UA при null. Старі й повторні запити не перезаписують новіші дані.
- Окремий запис встановлення за `installationId`; один API-клієнт на SHA-256 токена. Токени, cookie й паролі проксі зашифровані Fernet. У вебпанелі лише уривки token/cookie, повний UA.
- Проксі HTTP/HTTPS/SOCKS5: додавання, парсер, редагування, видалення, перевірка вихідного IP, запит зміни IP, вибір основної. Ваша проксі вже записана в локальному `.env` й імпортується в базу при першому старті.
- Перевірка клієнтів, пагінація Meta, усунення дублів акаунтів, запасний клієнт на той самий акаунт, денний Insights усіх кампаній без фільтра ACTIVE.
- SQLite WAL; точні гроші у мільйонних частках валюти; старе/нове значення та різниця у знімках. Окремі записи відправлень, спроби, помилки, статуси задач.
- Автоматичний інтервал 1/4/8/12/24 годин; Facebook та Keitaro початково увімкнені; комісія +10%; початок 01.09.2026; максимум 2 календарні місяці.
- **«Оновити зараз»** примусово запускає збір і експорт у будь-який момент, без очікування автоматичного інтервалу. Перемикачі інтеграцій враховуються. Повторні натискання не створюють паралельних задач одного типу.
- Дашборд за сьогодні/місяць, графік, окремі валюти, стан проксі, список кампаній без відповідності, журнал подій і відправлень.
- Фоновий обробник відновлює перервані задачі, наздоганяє пропущений збір, повторює помилки. systemd перезапускає процес після аварії та після перезавантаження сервера.

## Встановлення на Ubuntu/Debian

Рекомендовано окремий VPS з Ubuntu 24.04 або Debian 12/13, Python 3.11+. Для невеликого обсягу почніть з 1–2 CPU, 2 GB RAM та SSD. Потрібен домен, A-запис якого вказує на IP сервера. Наприклад, `spend.example.com`.

### 1. Встановіть пакети

Підключіться до сервера через SSH та виконайте:

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip nginx certbot python3-certbot-nginx
sudo useradd --system --home /opt/myraha-spend --shell /usr/sbin/nologin myraha
sudo mkdir -p /opt/myraha-spend
```

### 2. Завантажте файли

Через WinSCP/SFTP завантажте в `/opt/myraha-spend` папки `app`, `static`, `scripts`, `deploy`, а також `requirements.txt`, `constraints.txt` та `.env`. Якщо використовуєте Git, `.env` не потрапить у репозиторій — перенесіть його окремо. Для роботи не потрібні `.venv` із Windows, `.git`, `.wheelhouse`, `tests` чи `data` з чужого запуску.

Якщо ваш SSH-користувач не має прав на `/opt`, спочатку завантажте у свою домашню папку, а потім скопіюйте через `sudo cp -a` до `/opt/myraha-spend`.

```bash
cd /opt/myraha-spend
sudo python3 -m venv .venv
sudo .venv/bin/pip install -r requirements.txt
sudo mkdir -p data/spend backups
sudo chown -R myraha:myraha /opt/myraha-spend
sudo chmod 600 .env
```

Якщо `.env` ще немає: також завантажте `.env.example`, виконайте `sudo -u myraha python3 scripts/init_env.py`. Скрипт згенерує пароль та ключі і не змінить вже наявний `.env`.

### 3. Заповніть `.env`

```bash
sudo nano /opt/myraha-spend/.env
```

Обов'язково заповніть:

| Параметр | Що вказати |
|---|---|
| `KEITARO_URL` | `https://tracker.example.com` або `http://IP`, без `/admin` |
| `KEITARO_API_KEY` | Admin API-ключ Keitaro з доступом до потрібних кампаній і звітів |
| `APP_PASSWORD` | Уже згенеровано. Це пароль для входу в панель |
| `CLIENT_KEY` | Уже згенеровано. Скопіюйте в розширення |
| `ENCRYPTION_KEY` | Уже згенеровано. Не змінюйте для існуючої бази |
| `COOKIE_SECURE` | На сервері залиште `true` |

`INITIAL_PROXY` уже заповнено вашою проксі в локальному `.env`. Її реквізити не включені в Git. Після імпорту змінюйте проксі через вкладку «Проксі»; повторний запуск не відновлює видалену проксі.

### 4. Увімкніть службу

```bash
sudo cp deploy/myraha-spend.service /etc/systemd/system/myraha-spend.service
sudo systemctl daemon-reload
sudo systemctl enable --now myraha-spend
sudo systemctl status myraha-spend
curl http://127.0.0.1:8000/healthz
```

Очікувана відповідь healthz: `{"ok":true}`. Сервер слухає лише `127.0.0.1:8000`; назовні його відкриває Nginx.

**Одна служба, один процес, `--workers 1`.** Не запускайте другу копію з тією самою базою й не використовуйте `--reload` на сервері: у програмі один фоновий обробник. Паралельні процеси з цією базою не підтримуються.

### 5. Підключіть домен та HTTPS

Замініть `spend.example.com` своїм доменом у файлі:

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/myraha-spend
sudo nano /etc/nginx/sites-available/myraha-spend
sudo ln -s /etc/nginx/sites-available/myraha-spend /etc/nginx/sites-enabled/myraha-spend
sudo nginx -t
sudo systemctl reload nginx
sudo certbot --nginx -d spend.example.com
```

Certbot налаштує HTTPS; виберіть перенаправлення HTTP → HTTPS, якщо запитає. Якщо у вас firewall, відкрийте порти 80 і 443 та залиште відкритим SSH. Порт 8000 відкривати назовні не потрібно.

Відкрийте `https://spend.example.com`, введіть `APP_PASSWORD`. До отримання HTTPS не надсилайте token/cookie через публічний HTTP. Служба запускається автоматично; порожні ключі Keitaro або відсутні клієнти дадуть зрозуміле повідомлення в журналі.

### 6. Налаштуйте розширення

```text
VITE_API_URL=https://spend.example.com/fb_data/add
VITE_CLIENT_KEY=значення CLIENT_KEY із .env
```

Значення може задаватися в налаштуваннях самого розширення — див. його документацію. Для фонових запитів Chrome extension потрібен `host_permissions` вашого HTTPS-домену. Це не endpoint для запитів довільного сайту: відкритий CORS для вебсторінок не увімкнено.

Після ручного надсилання даних розширенням відкрийте «API-клієнти». Для schema 2 без UA клієнт збережеться, але збір чекатиме UA зі schema 3. Потім у «Проксі» натисніть «Перевірити», перевірте основну проксі та натисніть **«Оновити зараз»**.

## Як рахуються витрати

1. Перевіряємо основну проксі через HTTPS-запит IP. Без проксі запити Facebook не виконуються; автоматичного виходу напряму немає.
2. Беремо активних і ще не перевірених клієнтів, які мають UA та хоча б одну увімкнену установку. Клієнт, вимкнений вручну, пропускається.
3. Перевіряємо `/me`, завантажуємо всі сторінки рекламних акаунтів. Підтверджені помилки авторизації Meta `102/190` роблять клієнта неактивним. Таймаути, 429, проксі, збої сервера та помилки доступу до окремого акаунта його не вимикають.
4. Для унікального акаунта беремо першого клієнта, отримуємо campaign-level Insights з `time_increment=1`. Якщо він не спрацював, пробуємо наступного власника. Успішно зібраний акаунт повторно не запитуємо в цьому запуску.
5. Перша спроба акаунта охоплює весь дозволений період. Звичайний запуск — сьогодні та попередні 5 днів. Після довшого простою починаємо від останнього успішно зібраного дня. Усі запити обмежені датою початку та віком максимум 2 місяці.
6. Перш ніж зберігати результат, дочитуємо **всі** сторінки Insights. Часткову відповідь не записуємо. Якщо в повній успішній відповіді раніше відомий рядок зник, записуємо 0 і експортуємо виправлення.
7. Гроші — цілі мільйонні частки валюти. Комісія рахується через Decimal один раз від сирого Meta spend. Наприклад, 10.20 + 10% = 11.220000. Повторні запуски не додають комісію вдруге.

### Час

Денні періоди визначаються часовим поясом рекламного акаунта; UTC-межі зберігаються в базі, включно з переходами літнього часу. Поле `day` — локальна календарна дата, не UTC-доба.

`bucket_at` і `collected_at` — фактичний час збору з точністю до секунди. Повтор у ту саму секунду оновлює знімок; інакше пишеться новий. Різниця рахується від попереднього денного значення в `spend_latest`.

Поточний день зберігається як доступна на момент запиту денна сума Meta. Для Keitaro використовується стабільний денний діапазон `00:00:00–23:59:59` у часовому поясі акаунта.

Дашборд показує останні денні значення, а не суму всіх знімків. Валюти відображаються окремо без вигаданого курсу конвертації. «Сьогодні з комісією» — потенційна сума для експорту до зіставлення; це не підтверджена сума застосованих витрат у Keitaro.

## Keitaro: чи подвояться старі витрати

Ви уточнили, що раніше писали з фільтром `sub_id_2`. Нова програма використовує ту саму схему:

```http
POST /admin_api/v1/campaigns/KEITARO_CAMPAIGN_ID/update_costs
Api-Key: ...
```

```json
{
  "start_date": "2026-09-05 00:00:00",
  "end_date": "2026-09-05 23:59:59",
  "cost": "112.200000",
  "currency": "USD",
  "timezone": "Europe/Kyiv",
  "filters": {"sub_id_2": "META_CAMPAIGN_ID"}
}
```

Keitaro розподіляє повну вказану суму між кліками вибраного сегмента та оновлює їхні витрати. **Для тих самих кліків це заміна, а не додавання ще однієї суми.** Повтор після таймауту надсилає ту саму повну суму, тому арифметичного подвоєння не відбувається.

Важливо, щоб збігалися ID кампанії Keitaro, значення `sub_id_2`, часовий пояс і період. Кліки поза новим фільтром/періодом зберігають старі витрати. На першому запуску звірте одну кампанію та день із її звітом. Вимкніть старий імпортер для цих сегментів: два імпортери можуть по черзі перезаписувати витрати різними сумами.

Відповідності беруться зі звіту `/report/build`: `campaign_id + sub_id_2`, з пагінацією. Без відповідності витрати лишаються в локальній базі, кампанія показується на дашборді. Якщо один Meta ID є в кількох кампаніях Keitaro, денна сума з комісією **ділиться порівно** між ними (залишок micros — першим за ID). Сумарний спенд у Keitaro дорівнює Meta spend; повна сума в кожен сегмент не надсилається.

Кожна відправка має унікальний ключ Meta ID + Keitaro ID + день; змінені суми замінюють бажаний стан запису. Старі незмінені дні не надсилаються без потреби. Недавні дні періодично застосовуються знову: пізні кліки можуть змінити розподіл навіть без зміни суми. Ручне оновлення примусово повторює недавні дні та невдалі записи, а зміна комісії перераховує всі збережені дні.

«Прийнято Keitaro» означає `success=true`, тобто **задачу прийнято в чергу трекера**, а не гарантовано завершено. Keitaro може обробляти її 10–20 хвилин. Остаточні значення перевіряйте у звіті трекера. Фонові запуски експорту не частіше ніж раз на 30 хвилин; ваша ручна кнопка свідомо обходить це обмеження.

## Відновлення після помилок

| Ситуація | Що станеться / що робити |
|---|---|
| Проксі впала | Клієнти не стають неактивними; збір повториться. Виправте проксі → перевірте → «Оновити зараз» |
| Токен прострочений | Клієнт неактивний лише після підтвердженої помилки авторизації. Новий token створить нового клієнта; нові cookie/UA повернуть старого в unknown |
| Та сама авторизація відновилася | «API-клієнти» → «Перевірити знову», потім «Оновити зараз» |
| Keitaro недоступний | Окремі записи отримають `failed`, спроби й помилку. Наступний запуск повторить; є «Повторити експорт» |
| Програма впала між запитом і відповіддю | `sending` відновлюється як `failed`; повна сума безпечно надсилається знову |
| Сервер вимкнений кілька днів | systemd стартує після завантаження; збережений розклад і дата останнього збору дозволяють наздогнати період |
| Помилка одного акаунта | Інші продовжують; задача завершується з попередженням/помилкою, подробиці в журналі |
| Дані старші дозволеного віку | Більше не збираються й не експортуються; локальні суми/знімки/відправлення видаляються плановим очищенням |

Ручний експорт працює навіть коли Facebook недоступний: використовує останні збережені дані. В інтерфейсі видно час останнього збору. Повний збір не завершується помилкою лише через один клієнт.

Корисні команди:

```bash
sudo systemctl restart myraha-spend
sudo systemctl status myraha-spend
sudo journalctl -u myraha-spend -n 100 --no-pager
sudo journalctl -u myraha-spend -f
df -h
```

Після зміни `.env` потрібен `restart`; зміни у вкладці «Налаштування» діють без перезапуску. Перезапуск не вимагає очищати базу. Якщо закінчився диск, звільніть місце й перезапустіть службу.

## Резервні копії та оновлення

Зробити узгоджену резервну копію бази, навіть коли служба працює:

```bash
cd /opt/myraha-spend
sudo -u myraha .venv/bin/python scripts/backup.py
```

Окремо збережіть `.env` в захищеному місці. **Без ENCRYPTION_KEY неможливо прочитати токени з копії бази.** Не копіюйте лише live-файл `.sqlite` звичайним `cp`: активна WAL може містити ще не перенесені зміни.

Для відновлення: зупиніть службу, перейменуйте всю папку `data/spend` у резервну папку, створіть нову `data/spend`, покладіть backup як `spend.sqlite`, поверніть відповідний `.env`, встановіть власника `myraha`, запустіть службу. Не змішуйте відновлену базу зі старими `-wal`/`-shm` файлами.

Для оновлення коду: backup → `sudo systemctl stop myraha-spend` → заміна файлів коду → `.venv/bin/pip install -r requirements.txt` → `sudo systemctl start myraha-spend`. Не перезаписуйте `.env` та `data`.

## Локальний запуск і тести

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
python scripts/init_env.py
# У .env: COOKIE_SECURE=false лише для локального HTTP
.venv\Scripts\python -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
# Інший термінал:
.venv\Scripts\python -m pytest -q
```

Linux: ті самі команди з `.venv/bin/python`. Тести використовують тимчасову SQLite й підставні Meta/Keitaro; реальний спенд не змінюють.

Додаткова браузерна перевірка: встановіть `playwright` у тестове оточення та виконайте `python -m tests.browser_smoke`. Потрібен встановлений Chrome з дозволеною автоматизацією. Скрипт використовує тестову базу, перевіряє форми й ручне оновлення та зберігає знімки в `data/browser-check`. На поточному комп'ютері Chrome блокує remote debugging системною політикою, тому цей сценарій тут не завершений.

## Що можна зробити ще надійніше

1. Залишити один сервер і один обробник, SQLite та systemd. Для цього масштабу Redis/PostgreSQL додали б складності; до них є сенс переходити при кількох обробниках або великому обсязі.
2. Налаштувати щоденний backup і копію на інший сервер. Контролювати вільний диск та `/healthz` зовнішнім моніторингом.
3. За потреби замінити рівний поділ між кампаніями з одним Meta ID на розподіл за кількістю кліків у звіті Keitaro. Зараз сума завжди зберігається, частки однакові.
4. Для великої кількості кампаній перейти на bulk `/clicks/update_costs` і асинхронні Insights, з окремим тестуванням на вашому трекері. Поточний індивідуальний endpoint зручніший для контролю кожного сегмента, але повільніший.
5. За потреби додати перевірку фактично застосованих сум за звітом Keitaro через 20–30 хвилин. Зараз контролюємо прийняття запитів, а не завершення внутрішньої черги трекера.

- [Оновлення витрат у Keitaro](https://docs.keitaro.io/en/campaigns-and-streams/updating-costs-manually.html): перезапис вартості кліків і тривалість обробки.

- [Facebook Costs](https://docs.keitaro.io/en/third-party-integrations/facebook-costs.html): повторні перевірки попередніх днів.
- [Dolphin: частота експорту](https://docs.keitaro.io/en/third-party-integrations/dolphin.html): рекомендація не частіше години.
- [Meta Insights](https://developers.facebook.com/docs/marketing-api/insights/): API джерела спенду. Доступність токенів, permissions та підтримувану версію Graph потрібно перевірити на ваших акаунтах.

Справжній наскрізний запуск потребує вашого Meta token/UA/cookie, робочої проксі та URL/ключа Keitaro. Сам факт проходження локальних тестів не підтверджує їхню доступність.
